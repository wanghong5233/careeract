# CareerAct 产品需求文档

> 产品名称：**CareerAct**  
> 品类说明：你的个人职业 Agent  
> 产品口号：规划职业，并把下一步真正做完  
> 立项状态：已立项  
> 当前阶段：产品定义 / 首个闭环规划  
> 更新日期：2026-09-07

## 1. 产品定义

### 1.1 项目名称

**CareerAct** 由 `Career` 与 `Act` 组成：前者明确职业领域，后者强调 Agent 不只提供建议，还会把下一步实际执行。对外统一使用“你的个人职业 Agent”说明产品品类，不再将 `Act` 生硬翻译为“行动助手”。

名称能够覆盖求职投递、职业规划、准备训练和入职成长，不被限制在简历、Offer 或某一次招聘阶段。对外首次出现时使用完整形式：

> CareerAct｜你的个人职业 Agent

该名称已完成初步互联网与 GitHub 撞名检查；正式注册公司、域名或商标前仍需进行法律检索。

### 1.2 一句话定位

面向个人的 AI 职业行动平台：以求职投递为核心入口，以长期职业成长为持续价值，由 Agent 结合用户的职业背景规划下一步、直接执行任务，并将每次申请、训练、面试、Offer 和工作经历沉淀为可复用的职业资产。

### 1.3 产品范围

CareerAct 有三层相互依赖的定位：

1. **核心业务——求职投递**：服务校招学生等真实求职者，完成岗位筛选、材料准备、平台沟通、网申填表、投递和流程跟进；
2. **长期主体——职业项目管理**：把职业阶段视为持续项目，管理目标、能力、任务、里程碑、材料和关键决策；
3. **产品形态——统一职业 Agent**：用户可以在同一个 Agent 中讨论并处理所有职业问题，由 Agent 调用平台能力继续执行，不必再到其他通用 GPT 重复解释背景。

产品主体是围绕职业项目、材料、岗位、申请和任务组织的 Agent 工作台。聊天是下达任务、解释判断和处理审批的一种交互能力，不是产品的信息架构中心。

职业发展是持续多年的事业，不是一次校招活动。用户会反复经历：

> 认识自己 → 确定阶段目标 → 积累能力与证据 → 发现机会 → 判断岗位 → 申请与沟通 → 面试与 Offer 决策 → 入职发展 → 下一次选择。

产品需要维护这条长期链路。当前求职是第一条落地闭环，校招是开发者能够持续 Dogfood 的首个场景，但不是产品的最终边界。

### 1.4 目标用户

产品服务需要长期管理职业发展、机会和求职事务的个人。

首批用户优先选择与开发者需求相近的技术类校招生，因为他们：

- 同时处理多个岗位、渠道和申请版本；
- 拥有实习、项目、论文等较多职业材料；
- 需要在 BOSS 直聘、猎聘和企业官网持续发现机会、沟通和申请；
- 需要管理职位编号、额度、截止时间和招聘状态；
- 能够为产品提供高频、真实、可验证的反馈。

后续自然扩展到实习求职、跳槽、转岗和再就业场景。不同阶段共享同一份职业档案，不需要每次从空白简历重新开始。

### 1.5 核心问题

现有工具通常只解决简历生成、岗位推荐、自动填表或投递记录中的单点问题，无法维护一个人的长期职业上下文：

- 职业目标、硬约束、真实能力和对外材料彼此割裂；
- 入职后产生的新经历没有持续沉淀为可验证的职业资产；
- 岗位发现、申请版本、招聘沟通和流程状态无法关联；
- Agent 改写材料时缺少可靠事实边界；
- BOSS 直聘、猎聘和企业官网之间存在大量重复操作；
- 用户不在线时，新岗位、HR 消息和招聘通知无人处理；
- 面试和 Offer 决策无法准确引用实际投出的材料及长期目标。

### 1.6 核心价值

1. **长期职业档案**：持续积累事实、能力证据、目标、约束和关键决策；
2. **统一职业 Agent**：理解长期背景，回答职业问题，并将建议直接转化为任务和行动；
3. **主动执行**：持续获取信息、执行申请、处理招聘沟通并推动职业项目；
4. **跨渠道闭环**：贯通 BOSS 直聘、猎聘、企业官网及相关通知渠道；
5. **可信与可追溯**：正式内容有事实来源，外部动作有授权和执行证据；
6. **持续复用**：一次求职和一段工作产生的数据，会服务下一次职业选择。

### 1.7 产品边界

产品是个人职业 Agent，不是：

- 只在求职季使用的简历或投递小工具；
- 通用个人助理或通用 Computer Use 平台；
- 企业 ATS、招聘管理或猎头系统；
- 代做笔试、面试或编造职业经历的工具；
- 绕过平台风控、无差别骚扰招聘方的群发系统。

CareerAct 可以呈现通用 Agent 的交互形态，但领域边界始终是职业发展。Computer Use、模型和 Agent Runtime 是内部实现能力，不是产品定位。

## 2. 产品目标

### 2.1 长期目标

- 成为用户持续维护职业信息和职业决策的主工作空间；
- 成为用户处理职业问题的统一 Agent 入口；
- 主动接住分散在招聘平台、官网和通知渠道中的机会与沟通；
- 将职业规划、求职执行和入职后的能力积累连接起来；
- 像项目管理 Agent 一样持续推进职业目标、任务、准备和复盘；
- 让 Agent 在授权范围内持续工作，而不是等待用户逐条下达命令；
- 通过长期档案和历史决策形成跨求职周期的用户价值与粘性。

### 2.2 当前落地目标

第一阶段先验证完整求职闭环：

- 建立可长期维护的职业档案；
- 根据目标和约束判断真实岗位；
- 基于事实形成岗位申请材料；
- 在 BOSS 直聘、猎聘和企业官网筛选岗位、填写申请表并完成投递；
- 在无人值守状态下发现岗位、处理消息和整理信息；
- 围绕目标岗位调研公司、整理面经并组织刷题和面试训练；
- 让职业角色助手基于同一份生涯背景回答问题并发起平台任务；
- 关联申请、沟通、材料版本和后续招聘状态。

产品成立的证据是真实任务完成、重复使用和跨阶段数据复用，而不是功能数量或演示效果。

### 2.3 核心渠道

以下渠道属于产品必须解决的真实业务范围：

- **BOSS 直聘**：岗位发现、主动沟通、HR 消息、简历发送和状态跟进；
- **猎聘**：岗位发现、沟通、申请和流程跟进；
- **企业官网**：岗位筛选、当次申请表填写、附件上传、保存后核验和投递；
- **通知渠道**：招聘邮件、站内通知和后续可接入的授权信息源。

实现可以按开发阶段逐步交付，但不能把其中任何一类定义为产品范围之外。

## 3. 产品原则

### 3.1 长期目标约束当前行动

岗位判断和材料策略不仅考虑“能不能投”，还要考虑用户当前阶段目标、硬约束、能力积累和下一步可迁移性。Agent 提供证据与建议，关键职业选择仍由用户决定。

### 3.2 事实与展示分离

- 职业事实、能力证据和对外表达分别管理；
- 同一事实可以服务不同岗位方向，但不能被包装成不存在的经历；
- 无法确认的信息不能进入正式申请或自动回复；
- 历史申请使用的材料必须保持可追溯，不能被后续修改覆盖。

### 3.3 统一职业 Agent 入口

用户可以直接讨论职业方向、公司和岗位选择、材料表达、学习计划、刷题、面试、Offer 与入职发展。Agent 必须继承用户已经确认的生涯背景，并能把对话中的结论转化为职业项目、任务或具体执行流程，而不是只返回一段建议。

平台可以通过统一模型网关接入不同模型或用户自有模型账号，但用户不需要在不同模型产品之间搬运职业上下文。

### 3.4 Agent 主动执行

产品不能退化为等待提问的聊天工具。用户授权后，Agent 应主动获取外部变化、判断是否需要行动、执行允许的操作，并将结果和异常报告给用户。

### 3.5 托管与后台续跑分离

- **后台续跑**：用户已经发起某项任务，即使关闭页面，任务仍继续到完成、失败或等待人工；
- **无人值守托管**：用户开启一项长期服务后，Agent 主动巡检岗位、消息和通知，在授权范围内持续行动，直到用户关闭服务。

二者都需要可暂停、可撤销、可恢复和可追溯，但不是同一项能力。

### 3.6 结果必须经过真实验证

- 外部动作完成后必须读取真实结果；
- 网页编辑态内容不能作为完成依据；
- 填写、发送、申请和状态更新需要对应证据；
- 成功、部分完成、失败、跳过和结果不确定必须明确区分；
- 不允许把中断、超时或未知结果标记为成功。

### 3.7 Web 优先

产品以零安装 Web 工作台作为主要入口。用户可查看职业档案、任务、远程浏览器、沟通和报告；需要本机能力时再评估桌面端，不以桌面安装作为首版前提。

## 4. 核心产品对象

产品围绕长期业务对象组织，而不是围绕聊天消息组织：

- **职业档案**：教育、经历、项目、成果、技能及其证据；
- **职业目标**：阶段目标、发展方向和时间范围；
- **职业约束**：城市、岗位方向、薪资、通道及用户自定义边界；
- **职业项目**：围绕求职、能力提升、转岗或入职发展的目标、任务、里程碑和复盘；
- **能力账本**：已有能力、待补能力和入职后新增的可迁移证据；
- **机会与岗位**：来源、JD、公司、职位编号、通道和匹配判断；
- **申请材料**：基础材料、不同方向版本和单岗位锁定版本；
- **招聘沟通**：与招聘方的会话、事实回复、待处理问题和承诺；
- **网申任务**：一次针对具体岗位的申请执行，包括在渠道上定位岗位、填写申请表、上传材料、保存核验和投递结果；
- **申请与流程**：申请动作、材料版本、状态、面试和下一步事项；
- **准备与训练**：公司调研、面经、知识准备、刷题计划、练习记录和薄弱项；
- **职业决策**：投或不投、Offer 比较、入职与离职等决策及依据；
- **托管服务**：用户开启的岗位巡检、消息值班和信息整理任务。

这些对象必须相互关联，并在不同求职和职业阶段持续复用。

## 5. 核心产品流程

1. **建立生涯背景**：导入材料，确认事实与能力证据，设置阶段目标和约束；
2. **建立职业项目**：把阶段目标拆成机会探索、能力准备、求职执行和复盘任务；
3. **发现并判断机会**：巡检渠道，对照背景、目标、约束、历史和能力判断岗位；
4. **形成申请材料**：选择对应方向，基于事实修改并锁定岗位版本；
5. **筛选、填表与投递**：在招聘平台或企业官网定位岗位，按锁定材料填写申请表，核验后投递；
6. **调研与训练**：根据公司、岗位要求和招聘阶段组织公司调研、面经、刷题与模拟面试；
7. **招聘沟通与跟进**：主动触达、回复消息，并关联申请、通知和流程状态；
8. **比较并决策**：基于长期目标比较机会和 Offer，由用户做最终选择；
9. **入职后继续推进**：记录新能力和成果，复盘职业项目，为下一阶段提供依据。

## 6. 核心产品能力

### 6.1 职业规划、档案与项目管理

- 管理职业事实、原始材料和来源证据；
- 维护阶段目标、职业约束和优先级；
- 将职业阶段拆解为项目、里程碑、任务和复盘；
- 关联求职执行、能力准备和长期发展计划；
- 区分真实能力、待补能力和对外展示版本；
- 持续记录学习、项目与工作成果；
- 支持职业目标和约束随人生阶段调整；
- 保留历史版本及当时的决策背景。

### 6.2 统一职业角色助手

- 基于用户已经确认的生涯背景回答职业相关问题；
- 覆盖方向选择、能力分析、公司与岗位、求职策略、学习准备、面试、Offer 和入职发展；
- 在不同对话和阶段保持对用户目标、事实、约束与历史决策的一致理解；
- 把建议转化为平台中的项目、任务、材料修改、调研、训练或投递流程；
- 能够调用不同模型处理具体任务，但保持统一的职业角色和上下文；
- 清楚区分事实、分析、建议和由用户决定的事项。

### 6.3 机会发现与岗位决策

- 从 BOSS 直聘、猎聘、企业官网及授权来源获取岗位；
- 解析 JD、公司、职位编号、城市、薪资和招聘通道；
- 对照职业目标、事实、硬约束和历史申请进行判断；
- 检查重复申请、额度、截止时间和通道冲突；
- 说明推荐、跳过或升级给用户判断的依据；
- 持续监控新岗位和已有机会的变化。

### 6.4 申请材料

- 基于事实维护多方向材料；
- 针对岗位生成和锁定申请版本；
- 展示修改 Diff、理由和事实来源；
- 支持审批、拒绝、继续修改和回滚；
- 处理字数、格式和版面约束；
- 保证面试准备引用实际投出的版本。

### 6.5 招聘平台沟通

BOSS 直聘、猎聘上的岗位筛选、申请表填写和投递见 6.6。本项只覆盖与招聘方的会话和平台内触达。

- 按用户策略主动触达招聘方（打招呼、沟通卡片等）；
- 巡检未读消息和招聘方主动沟通；
- 对可由职业档案举证的常规问题自动回复；
- 按授权发送正确版本的简历或平台简历卡；
- 将技术问题、时间承诺、面试选择和未知意图升级给用户；
- 保留沟通内容、发送依据和处理结果。

### 6.6 网申筛选、填表与投递

这是当前求职闭环里最高频、最重复的执行能力，不是可选项，也不是“有浏览器就能做”的实现细节。用户需要 Agent 在真实招聘页面上完成：找到岗、填对表、核验后投出去。

覆盖企业官网，以及 BOSS 直聘、猎聘等需要填写申请信息或投递简历的页面。官网尤其要区分「个人中心简历」和「当次岗位申请表」：只完善前者不等于已申请。

- **岗位筛选**：在目标公司或平台的招聘页按职业目标、硬约束、城市、通道、额度和职位编号筛选可投岗位；排除已投、超额度、届次不符和用户禁投范围。
- **进入当次申请**：打开该岗位的申请表或投递页，而不是只编辑通用简历。
- **自动填表**：按职业档案和该岗锁定材料填写文本、列表、日期、下拉、级联、附件和其他必填项；有旧值先覆盖，不追加脏数据。
- **材料与格式约束**：遵守字数、列表格式、链接口径、附件版本和岗位页实际字段结构；没有的栏位不编造。
- **保存后核验**：暂存或保存后重新读取预览/结果页，核对关键字段是否真正写入，不以编辑态瞬时值为完成依据。
- **投递**：按授权执行提交，或填完后交给用户确认提交；禁止在结果未核验、字段缺失或重复投递风险未排除时提交。
- **异常与介入**：登录、验证码、风控、无法映射的字段和不可逆确认，暂停并立即交给用户；浏览器会话仍有效时从原页面继续。会话超时且确认没有发生外部写操作时，才从已确认的业务进度重新执行；结果不确定时先人工对账，不得谎称恢复了未保存页面。
- **结果回写**：记录申请编号、投递时间、使用的材料版本、成功/失败/待确认，并写入申请与流程。

云端浏览器、页面操作和人工接管是实现手段，不作为本项的产品需求表述。

### 6.7 招聘流程、准备训练与职业决策

- 关联岗位、沟通、申请版本和招聘状态；
- 从授权通知源提取笔试、面试、拒信和补充材料要求；
- 调研目标公司的业务、岗位、团队和招聘要求；
- 汇总、去重和分析面经，并与具体公司、岗位及面试阶段关联；
- 根据岗位要求和用户能力缺口生成刷题、知识复习、项目讲解和模拟面试计划；
- **模拟面试（后续能力）**：基于实际投递的简历版本、JD、公司信息和面经进行中文或英文的文字或实时语音模拟问答，针对回答连续追问，并在结束后形成反馈、薄弱项和后续准备任务；该能力不进入首个投递闭环，后续可作为独立功能入口接入统一职业 Agent；
- 记录训练进度、反馈和薄弱项，动态调整准备任务；
- 生成待办、提醒和基于实投版本的面试准备材料；
- 保存状态变化和关键时间节点；
- 按用户目标和约束比较 Offer，不替用户做最终决定；
- 将入职后的经历和成果重新沉淀到职业档案。

### 6.8 已发起任务的后台续跑

用户关闭页面后，已经发起的材料分析、岗位判断、申请材料生成、岗位筛选、申请表填写、核验和投递任务应继续执行，直到：

- 成功完成；
- 明确失败；
- 外部结果不确定；
- 等待登录、验证或用户输入；
- 用户暂停或取消。

### 6.9 无人值守托管

无人值守是一项由用户明确开启的长期值班服务。开启服务不等于只执行一次，执行一次也不等于自动开启长期服务。

托管授权必须明确记录：适用平台与岗位范围、允许的动作、材料版本规则、频率或数量上限、有效期和撤销状态。只读巡检与信息整理可以在托管开启后自动执行；提交申请、发送简历和对外回复默认关闭，只有用户对相应范围明确授权后才能无人值守执行。一次授权不能自动扩展到其他平台、材料、动作或无限期限。

托管服务包括：

- **自动发现**：按工作时段巡检 BOSS 直聘、猎聘、官网和授权信息源；
- **自动判断**：按职业目标、硬约束、匹配规则、额度和历史记录筛选机会；
- **自动触达与投递**：对符合授权条件的岗位主动沟通、发送简历，或完成筛选、填表与投递；
- **自动回复**：处理可由职业档案举证的常规问题和预定义平台动作；
- **自动整理**：汇总岗位、未读消息、邮件和招聘通知，更新状态与待办；
- **报告与升级**：持续报告已执行、已跳过、失败和需要用户处理的事项。

对于技术追问、事实不足、未知意图、时间承诺、面试接受或拒绝等超出授权范围的事项，Agent 必须暂停该动作并通知用户。用户处理后，应重新执行原任务，而不是仅修改状态。

无人值守必须遵守平台和用户边界：

- 按用户与平台执行频率、并发和数量限制，禁止无差别海投或批量骚扰；
- 发现验证码、平台风控提示、账号异常或疑似封禁时停止自动写操作并通知用户；
- 不绕过平台安全机制，不伪装或编造用户身份与职业事实；
- 投递和消息使用幂等标识与历史检查，避免重复提交或重复发送；
- 用户撤销授权后，尚未执行的相关任务必须停止。

### 6.10 结果报告与敏感操作记录

用户需要了解任务结果和需要自己处理的事项，不需要查看 Agent 的内部运行轨迹。

- 每次筛选、填表、投递、沟通或状态变更完成后，向用户给出结果报告：做了什么、结果如何、还要不要处理；
- 发送简历、提交申请、接受或拒绝面试等敏感或不可逆操作，必须有事后报告，并关联当时使用的材料与授权；
- 报告可附带结果证据（申请编号、预览页关键字段、状态文本），用于确认“已经填上/已经投出”；
- Agent 的逐步观察、内部判断、工具调用和完整运行轨迹只用于后端运维、排障与审计，不属于前端产品需求。
