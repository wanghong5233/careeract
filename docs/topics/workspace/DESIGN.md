# CareerAct 工作台形态 · 第一版可视提案

状态：待用户评审，未定稿。更新：2026-10-01。
依据：PRD 1.3、3.2–3.8、4、5、6；ARCHITECTURE 2.1、2.4、3.1、3.6–3.8。
这是把需求翻译成可见交互的方案，不修改 PRD，不代表业务能力已经实现。

## 先回答：为什么值得做这个作品

项目的首要价值是可展示、可复现、自己愿意反复使用的 Agent 应用。开发者同时处于求职与
能力积累阶段，时间和预算有限。因此要让一次演示展现完整产品判断：理解背景、提出行动、
产出可用内容、允许人修改、执行时守住边界、留下可继续利用的结果。

只增加一个聊天入口不能证明这些；大量资料表单也不能证明这些。视觉上的新意要来自人的
工作方式发生变化：用户围绕目标委托工作、审阅结果，而不必先搬运上下文、配置流程、填满字段。
竞争力能否成立，仍需真实任务完成率、复用率和使用反馈验证；不能由原型外观或 Star 数保证。

已按本次授权阅读所有者的求职目标与投递策略，观察其目录中目标、实习、项目材料、岗位、
申请记录、准备训练和长期背景的关联。私人正文不复制进本稿或原型，原型使用虚构资料。

## 产品主线

**职业项目是持续空间，一项委托是工作单元，可编辑成果是主要工作对象。**

```text
长期职业背景与证据
        ↓ 选择相关上下文
职业项目 ──→ 表达意图 / 直接打开已有内容
                 ↓
              Agent 推进一项工作
                 ↓
          可审阅成果、待确认问题、下一步
                 ↓
       修改 / 接受 / 继续准备 / 授权一次执行
                 ↓
       结果证据 → 项目记录 → 经确认的新职业资产
```

聊天承载意图和澄清；任务、内容与结果可脱离某段聊天继续找到。Agent 的工作存在感来自当前
任务、产出和可继续的动作，不靠一列长思考日志。技术 Trace 不进入日常工作区。

### 三个需要实际做出来的区别

1. **上下文随工作走。** 从岗位开始准备材料，自动带入相关背景、来源与约束，用户能查看
   本次用了什么。不是把全部职业资料永久塞进每次请求。
2. **在成果上协作。** 正文阅读、局部编辑、Agent 修改建议是同一份内容的不同状态；审阅
   Diff 后继续执行，不在聊天、表单和独立“预览版”之间重复同步。
3. **行动回到职业积累。** 申请关联锁定材料与回执，面试准备引用实投版本，准备中的新
   证据经确认后进入背景。另一个“工程作品”项目可以独立推进，不必依附某次申请。

创新先检验这三个关系能否减少真实工作，不预建自由节点画布、复杂多 Agent 可视编排或
动态生成整套导航。产品界面要稳定，Agent 可改变任务内容，不随意重排用户的工作空间。

## 信息组织与交互

| 层次 | 用户看到什么 | 行为 |
| --- | --- | --- |
| 全局 | 开始工作、查找内容、职业项目、可复用背景与材料 | 随时从意图或已有内容进入；设置与连接退到次要位置 |
| 项目 | 目标、正在推进的工作、待审阅成果、资料与阶段计划 | 首页直接恢复工作；不放装饰统计，不要求先创建全部对象 |
| 当前工作 | 主区的成果或浏览器，旁边的委托、进度、上下文与继续输入 | 一次突出一个成果；相关内容按需打开，保留当前位置 |
| 内容 | 阅读、修改建议、直接编辑、来源与版本 | 一个正文，不并排维护两份独立可写真相；复制纯文本不带 Markdown 标记 |

侧栏保留项目、待处理工作和跨项目资产；项目内用工作视图区分计划、机会、申请、准备、
决策与资料。具体申请和任务从列表进入，不把每条历史记录塞进侧栏。完整需求须有可发现的
入口与代表交互；尚未实现的业务明确预留，不因首条展示路径暂时用不到而隐藏产品范围。

### 档案、材料与原件

用户可先导入、粘贴、讲述或直接修改。原始 PDF/DOCX/TXT 保留为来源；职业档案保存已确认
事实；简历、准备稿和报告保存相应表达与版本。它们可以在同一工作区关联，但不能混成
同一个可覆盖文件。事实确认、接受改稿、授权申请是三个不同动作。

不要求用户选择数据库格式。正式实现延续 PostgreSQL 领域数据、Tiptap 内容与对象存储
原件；可提供纯文本、Markdown 或 PDF 导出。界面主态是可阅读内容，结构化核对只在执行
需要补充字段时局部出现。原型不实现解析、Tiptap、版本后端或真实文档导出。

### 代表性路径

1. 回到“2027 秋招”，看到已经整理好的材料与两处待审阅建议。
2. 打开材料，原位比较修改；查看来源；接受一处、保留另一处，或继续要求调整。
3. 所有建议处理完后，进入申请准备；显示锁定版本和具体岗位。
4. 在申请预览中核对，必要时接管；授权仅限本次申请。
5. 读取结果并形成回执。未知结果转人工核实，不提供自动重投。
6. 从实际申请材料进入项目讲述与面试准备，把薄弱项加入项目任务。

机会研究作为另一条入口：一次委托返回带来源、匹配原因和未知项的候选；用户可继续研究
或进入申请。定期关注由单独授权开启，仅覆盖配置的来源；不承诺全网实时监控。

## 第二轮形态研究与候选方案

研究日期：2026-10-01。这里记录公开产品行为和对 CareerAct 的推导，不把竞品的内部规范、
模型能力或商业指标当作事实。官方页面在本环境部分受访问限制，因此以专题已有的官方正文
记录、公开产品页面和可见交互为依据；未登录 Manus，也没有把生产能力当作验收证据。

### 研究结论：Agent-native 不是“聊天框加按钮”

| 观察对象 | 可复用的交互模式 | 对 CareerAct 的启发 |
| --- | --- | --- |
| [Codex 项目与工作](https://learn.chatgpt.com/codex/projects)、[Codex 文件工作](https://learn.chatgpt.com/codex/artifacts-viewer) | 项目保存上下文；不同工作可以并行；文件、Diff、编辑和审核靠近同一成果；自动化结果进入待处理队列 | 把职业项目和可编辑成果作为一级对象；聊天只负责委托、解释和追问；等待用户决定的结果不能藏在历史消息里 |
| [Canvas](https://openai.com/zh-Hans-CN/index/introducing-canvas/) | 在成果上直接编辑；可针对局部内容提出修改；保留版本恢复 | 材料、准备稿和报告都应是“可继续工作的内容”，Agent 建议必须落在内容上并可撤回 |
| [Deep research](https://openai.com/index/introducing-deep-research/) / [Operator](https://openai.com/index/introducing-operator/) | 先明确目标和范围，再执行检索或工具动作；展示来源、阶段结果、异常和需要用户确认的节点 | 用“正在整理 / 等你确认 / 需要核验 / 已完成”表达业务状态，不暴露完整内部推理轨迹 |
| [Manus Projects](https://manus.im/docs/features/projects) | 项目共享指令、文件和任务上下文；任务产生可继续的结果 | 相关背景应随工作携带，并显示本次实际使用的资料和版本，而不是让用户重新粘贴 |
| [Manus Cloud Browser](https://manus.im/docs/features/cloud-browser) | 在需要时观察执行现场并接管；浏览器只是任务中的一个执行面 | 只有进入填表、核验或人工介入时才展开浏览器；授权、租约和结果验收比“看起来像人在操作”更重要 |
| Replit Agent / Devin 类编码 Agent 的公开交互 | 从自然语言目标进入计划、改动、运行结果和可审阅差异 | CareerAct 可以借鉴“意图 → 工作单元 → 可审阅成果 → 可继续动作”，但不复制代码 Agent 的终端中心布局 |

这些产品共同点是**工作对象先于对话**：用户看见目标、上下文、成果、状态和下一步，
再决定是否打开对话、细节或执行现场。它们也共同避免把 Agent 的全部思考过程当作产品价值：
用户需要的是依据、证据、风险和可接手的结果。

### 候选形态 A：当前工作（Objective-first Workspace）

**核心体验**：用户回到某个职业项目，首先看到“现在最值得推进的一件事”。Agent 以工作单元
存在：它带着目标、使用的上下文、产生的成果和待用户决定的事项。用户可以从一句话、一个岗位、
一份材料或一个变化直接开始，不必先维护完整表单。

**首屏结构**：

```text
CareerAct / 2027 秋招                         查找   开始工作

找到能持续积累 Agent 与系统能力的第一份工作
本周焦点：星野 · Agent 研发申请                  已准备 · 等你审阅
┌────────────────────────────────────────────────────────────┐
│ 申请材料 · Agent 工程方向                                 │
│ 2 处修改建议 · 3 份来源 · 尚未对外提交                     │
│ 查看依据   审阅材料   继续准备                             │
└────────────────────────────────────────────────────────────┘

正在推进                 需要我决定                最近变化
准备技术一面              是否提交 XY-18            2 个官网岗位更新
整理项目讲述              到岗时间如何回复          1 条来源读取失败

告诉 CareerAct 你想推进什么……       [职业项目 · 已确认背景]
```

**Agent 角色**：CareerAct 是稳定的职业行动伙伴，有清晰的事实边界和授权边界；渡鸦只承担
识别和状态标记，不做拟人头像、情绪动画或虚构人格。Agent 的存在通过“它正在推进什么、用了
什么背景、为什么停下、下一步是什么”体现。

**对象组织**：职业项目是容器；当前工作是可恢复单元；档案、岗位、材料、申请、任务和报告
是工作单元的关联对象。完整入口仍存在，但侧栏只保留项目、待处理和跨项目资产，详细菜单在
项目页或查找中出现。

**复杂度与价值**：沿用现有 Next.js 壳、AG-UI、领域 API 和材料组件，新增工作单元/上下文
关系及首页投影，复杂度中等。它最能用一条 90 秒路径展示“理解背景 → 产出材料 → 人审阅 →
授权执行 → 结果回写”，也最贴合真实求职工作区。

**风险**：如果只有项目列表和待办，它会退化成普通项目管理工具。必须让 Agent 产生真实的
可审阅成果、依据和下一步，并把结果回到职业资产；不能只换一套颜色和标题。

### 候选形态 B：职业 Agent Desk（Agent-first Workspace）

**核心体验**：首屏是一个职业 Agent 的工作台。用户用自然语言、意图卡片或已有对象启动工作，
Agent 先提出范围和计划，再把结果分派到材料、机会、准备或申请视图。

**首屏结构**：中央为当前委托和阶段结果；左侧为项目/上下文；右侧为“需要我决定”和授权；
下方是最近成果。聊天和意图输入更突出，但成果仍需打开到正文或时间线中审阅。

**复杂度与价值**：需要意图路由、上下文选择、会话恢复、任务投影和跨对象导航，复杂度高。
代表作辨识度强，适合展示统一职业角色；但最容易退化成“一个更漂亮的聊天框”，也会把用户
推回等待模型回答，削弱职业项目的长期结构。

### 候选形态 C：职业行动时间线（Evidence / Timeline Workspace）

**核心体验**：以目标为起点，把机会、材料版本、申请状态、面试、决定和成长证据串成可追溯的
职业时间线。Agent 负责解释变化、补齐关联和提出下一步。

**首屏结构**：顶部为阶段目标与当前风险；中央为按时间排列的行动流；右侧为选中事件的来源、
材料快照和下一步。用户可以从任意事件回到原文或启动一项工作。

**复杂度与价值**：需要事件模型、来源冲突、状态历史和跨项目投影，复杂度中高。对真实求职
跟踪非常有价值，也能展示“职业资产持续复用”；但早期数据不足时页面会空，且时间线容易变成
密集后台或静态档案，不能替代当前工作入口。

### 方案取舍

| 维度 | A 当前工作 | B Agent Desk | C 行动时间线 |
| --- | --- | --- | --- |
| 真实求职可用性 | 高 | 中 | 高 |
| 首屏易懂程度 | 高 | 中 | 中 |
| Agent-native 辨识度 | 高（靠工作单元） | 很高 | 中高 |
| 首条路径实现成本 | 中 | 高 | 中高 |
| 空数据时的表现 | 稳定 | 稳定 | 较弱 |
| 主要风险 | 像项目管理 | 像聊天产品 | 像后台时间线 |
| 代表作展示 | 强，路径完整 | 强，角色鲜明 | 强，数据关系清楚 |

## 推荐形态：A 为骨架，吸收 B 的角色感和 C 的证据关系

推荐 **当前工作（Objective-first Workspace）**。它直接回答职业用户每天的问题：现在最值得
推进什么、Agent 已经做了什么、哪些事需要我决定。它不要求先建完整档案，也不把所有能力压缩
成聊天；同时可以在后续接入 Agent Desk 的自然语言委托和行动时间线的历史证据，而不重做信息架构。

推荐首屏的四个稳定区域：

1. **阶段目标**：一句真实目标、当前约束和项目范围；不使用营销口号或虚构完成率。
2. **当前工作**：一个主工作单元，展示状态、成果、来源、版本、风险和主要动作。
3. **需要我决定**：只列会阻止安全推进的选择，例如接受修改、确认时间、授权提交、核对未知结果。
4. **最近变化与可复用背景**：机会/通知/材料变化的摘要，以及进入背景、材料、申请和准备的入口。

Agent 输入框是全局可见但视觉次要的“开始另一项工作”；上下文由当前项目自动带入，用户可以
移除或补充。右侧 Agent 详情只在有活动工作时出现，可折叠；日常不展示长 Trace。

### 关键交互流程

```text
一句意图 / 一个岗位 / 一份已有材料
          ↓
选择或确认项目与本次上下文
          ↓
Agent 创建工作单元：目标、范围、状态、预期成果
          ↓
读取来源 → 形成可编辑成果 / 判断 / 待核实项
          ↓
用户审阅、修改、接受或继续追问
          ↓
安全动作单独授权（申请、发送、连接、托管）
          ↓
确定性读取结果 → 报告、状态历史、材料快照
          ↓
经确认的新事实回到职业背景，供下一项工作复用
```

工作状态只使用用户能行动的业务语言：`已受理`、`整理中`、`等你审阅`、`需要核验`、
`等待输入`、`已完成`、`部分完成`、`失败`、`结果未知`。内部 Agent Run、工具链和推理日志
进入运维诊断，不作为首屏信息架构。

### 数字职业伙伴的边界

可以有稳定的 CareerAct 角色、名称、渡鸦标记、记忆摘要和行为承诺，但不引入虚拟人、头像、
语气表演或持续陪聊。角色只有在三件事上改善协作才值得保留：

- 记住用户确认过的背景、目标、约束和历史决定；
- 在每项工作中说明使用了什么、为什么停下、需要用户决定什么；
- 把成果和结果回写到职业项目，避免每次从聊天重新开始。

如果角色只增加问候、气泡或动画，就删除它；产品身份应来自工作质量和证据关系。

## 最小可见验证与实现顺序

本轮不再制作一套与正式前端并行的完整静态应用。先用现有原型做结构评审，并提供一个只展示
推荐首屏的最小交互草图：切换“正在推进 / 需要我决定 / 最近变化”，点击当前工作打开成果，
点击需要决定项看到依据和下一步。该草图只用于本次可见沟通，不进入仓库、不成为第二套 UI。
用户确认信息组织后，直接在 `apps/web` 正式壳中实现，不复制原型组件。

正式实现按以下顺序推进：

1. **首屏投影**：项目目标、当前工作、待用户决定和最近变化；先用真实领域读取，不接外部写操作。
2. **工作单元与上下文**：把 Agent 委托、成果、关联对象和业务状态持久化；页面重开可恢复。
3. **一条成果协作路径**：选择已有材料 → Agent 提议 → Diff 审阅 → 版本保存 → 回到申请准备。
4. **一条结果回写路径**：任务状态、申请/材料快照和结果报告关联；未知结果转人工，不自动重试。
5. **再接机会研究或浏览器执行**：先限定来源和动作，测量成本、质量、风控和结果核验。

首条路径的验收不是“页面像参考产品”，而是用户能在不重复粘贴背景的情况下完成：打开当前
工作、理解依据、处理一个决定、继续编辑成果，并在刷新后找回同一状态。视觉验收关注中性底色、
留白、中文长文本、对齐、键盘焦点和窄屏重排；不再用绿色主题、固定三栏或全量 Agent 面板作为默认。

## 实现路径与待验证边界

| 增量 | 交付 | 前置/主要风险 |
| --- | --- | --- |
| 当前：形态评审 | 在现有原型复核全部需求入口与代表交互 | 用户确认整体组织与主要路径；不修改现有业务页 |
| 第一条真实路径 | 选定现有资料 → 局部 Agent 提议 → 审阅 → 版本保存 → 再打开 | 领域材料版本、来源、所有权、并发；现有 profile version 不是历史版本系统 |
| 任务与项目连续性 | 项目归属、任务状态、成果关联、退出后恢复 | Agent Run 不是业务状态；需领域 API 与持久任务边界 |
| 研究与受控执行 | 一个限定来源研究或一个可验收站点任务 | 成本、质量、风控、授权与未知结果；不一次承诺全渠道 |

原型有本地筛选、状态追加、草稿编辑/版本恢复、委托记录、固定 Diff、任务控制和托管授权
演示。自由输入由用户选择工作去向，不伪装模型理解。状态只在页面内存，刷新重置。
导入解析、富文本选区、真实检索/训练/语音、导出及连接管理只预留功能 UI；完整边界见下表。
各页面使用固定场景，尚未实现任意岗位/项目间的动态关联，更没有接入业务 API。

### 评审只先决定这三件事

- 这条“背景 → 材料 → 申请 → 准备 → 新证据”的连续体验，是否值得作为代表作的首条展示路径？
