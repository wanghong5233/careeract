# BOSS 招聘沟通

## 目标

CareerAct 下一阶段先解决用户当前最高频的真实任务：在 BOSS 直聘上识别符合职业目标和硬约束的岗位，向对应招聘方发送有依据的首次招呼，并能确认结果、记录证据和生成报告。

这项能力仍由职业 Agent 组织上下文、判断和后续任务；岗位、沟通、授权、执行和结果属于 CareerAct 领域状态，不以聊天记录或一次 Agent Run 作为唯一依据。

## 首个可验收闭环

1. 用户在隔离浏览器中登录 BOSS 直聘并保持会话。
2. Agent 读取用户明确指定的岗位或当前岗位页，保存岗位来源、公司、职位、地点、薪资和页面状态。
3. 按职业目标、硬约束、已确认事实和历史沟通判断是否适合；缺失或冲突信息标记待核实，不自动触达。
4. 基于可举证的职业事实生成一条打招呼草稿，展示岗位依据、引用事实和未知项。
5. 用户开启仅限 BOSS 打招呼的短时授权，明确岗位范围、数量上限、材料范围和有效期。
6. 通过站点适配器发送一次消息，发送后重新读取页面核验；成功、失败、待人工核对分别落库并生成结果报告。

首版不自动回复 HR 后续问题，不发送简历卡，不处理验证码或风控，不在结果未知时重试，不把一次授权扩展到其他平台或其他外部动作。

## 业务边界

- 发送对象是招聘方会话，不做无差别群发；每个岗位和会话使用幂等检查。
- 消息只能使用职业档案和已确认材料中的事实，不能编造经历、技术栈、到岗时间或承诺。
- 页面读取、模型生成和对外发送分别记录处理目的；浏览器登录态由用户在隔离 Profile 中直接输入，CareerAct 不接收明文密码或验证码。
- 发送结果必须由页面状态或站点适配器再次确认；网络断开、页面跳转或回读失败都进入待人工核对。
- Playwright 负责已知 BOSS 页面和最终核验；页面结构未知时可产生候选动作，但必须回到确定性适配器确认。

## 交付顺序

### 第一个增量

- 岗位与招聘会话领域对象、归属和状态历史。
- BOSS 站点只读适配器：岗位摘要、招聘方会话定位、登录/验证码/风控状态。
- Agent 工具：读取岗位、判断匹配、生成打招呼草稿；草稿先进入用户可见的待发送状态。
- Web 结果卡：岗位依据、草稿、授权范围、执行状态和结果证据。

### 第二个增量

- Temporal 沟通 Workflow 与浏览器 Activity。
- 短时、限平台、限岗位、限数量授权。
- 发送前检查、发送后确定性回读、未知结果对账和撤销未执行任务。
- 真实合成岗位和隔离 BOSS 会话验收后，才开放用户自己的真实岗位。

### 后续

- 未读消息整理和常规问题回复。
- 简历卡发送与岗位锁定材料关联。
- 用户明确开启的定时巡检和有限自动打招呼。

## 验收证据

每次执行至少保存岗位标识、会话标识、授权标识、消息版本、尝试时间、页面核验摘要和最终状态。截图或页面原文只在满足隐私和保留策略时保存，不把登录态、验证码或敏感字段写入普通日志。

必须分别验证：未登录、验证码、风控、岗位不匹配、重复会话、消息发送成功、发送结果未知、用户撤销授权和浏览器租约冲突。任何未知外部结果都不能显示为成功，也不能自动重发。
