# 工作台交互规格：档案与材料

更新：2026-09-29。读者：产品维护者与实现这些交互的 Agent。

本文维护档案、材料和 Agent 编辑的用户路径与验收约定。产品原则按本次讨论收口，布局、
按钮措辞和审阅粒度是待交互原型验证的设计方案，不能当成已实现能力。
实际状态见 [STATUS](../engineering/STATUS.md)，开发流程见 [DEVELOPMENT](../engineering/DEVELOPMENT.md)。
本文件只包含可公开的交互约定，不收录个人材料、截图、身份信息或私人求职策略。
跨页面视觉、文案与质量检查统一见[产品设计原则](DESIGN_PRINCIPLES.md)，本文只维护具体流程。

## 1. 产品原则

- 以职业内容和任务成果为主区。用户能打开、阅读、修改和审阅自己的内容；对话用于提出
  目标、补充上下文、解释修改，结果落到对应业务对象，不只留在聊天消息里。
- 档案默认是可阅读的职业背景页，不是整屏展开的数据库表单。先导入、粘贴或讲述已有
  经历，再针对缺失与冲突补充；允许直接手工开始，但不强制完成整份问卷才能使用。
- 借鉴文档工作台的简洁与渐进呈现：一个主要工作区，按需展开 Agent、来源、历史和审阅。
  不照搬 IDE 的终端、Git 操作和代码目录，也不为尚未开放的功能摆满空卡片。
- 人与 Agent 都能持续编辑。用户直接编辑和 Agent 提议最终经过同一套领域校验与版本控制。
- 确认、保存草稿与对外使用具有不同含义。界面用就地状态和清晰动作表达，避免每次输入
  都弹窗或要求勾选声明，也不把已保存草稿显示成已确认事实。

## 2. 用户打开的是什么

| 对象 | 默认展示 | 编辑与边界 |
| --- | --- | --- |
| 职业档案 | 按教育、经历、项目、成果等组织的可读背景页，保留叙述 | 点击段落编辑；学校、学位、日期等只在需要时出现小范围字段控件；支持 Agent 提议 |
| 来源资料 | 保留文件名的原文或预览，可定位引用段落 | 导入原件不原地覆盖；更新文件形成新来源版本，已有事实引用仍指向原版本 |
| 简历与申请材料 | 当前选定方向/语言版本的可编辑正文 | 可从导入原文建立可编辑副本，也可基于事实生成；人工编辑、Agent 修改、审阅与历史 |
| 目标与偏好 | 简洁自然语言，必要时突出硬约束 | 属于内部职业上下文，不默认进入对外材料 |

“查看原文”是一等入口。TXT/Markdown 可以直接阅读；PDF/DOCX 提供原件预览或下载，
转换后的可编辑正文明确标为副本，不承诺保留 Word/PDF 全部版式或直接改写原件。
用户可在保留原文件名的材料文档中持续编辑，导入原件在来源入口查看，不要求用户手动
维护两份内容或每次更新重新导入。
修改来源不会自动覆盖档案，修改简历措辞也不会自动改写职业事实。
含私人备注的来源不能因被导入就整体成为对外材料。

## 3. 工作台布局与视觉方向

桌面布局草图；面板按任务展开，不要求始终占据三栏：

```text
导航 / 内容列表       当前打开的档案或材料              Agent（可收起）
                     标题 · 草稿/已确认                当前文档 / 所选段落
职业背景             正文与就地编辑                    输入修改目标
材料                 待审阅修改（出现时展开）          简短进度与修改说明
                     来源 / 历史（按需打开）            打开对应修改
```

- 首次使用主要动作是“导入资料”，同时允许粘贴内容或讲述经历；没有材料也能开始。
- 有内容后恢复用户正在处理的对象；正文优先，减少宣传性大标题、统计卡片和层层边框。
- 打开材料或选择正文时可直接“让 Agent 修改”。用户能看到本次操作针对整篇还是选段，
  能选择相关材料与岗位上下文；无需重新粘贴全文进聊天框。
- 正文排版、色彩、控件与动效遵循[产品设计原则](DESIGN_PRINCIPLES.md#3-视觉基础)。
- 窄屏一次显示正文、Agent 或审阅中的一个，切换后保留文档、选区和输入，不挤成三列。
- 保留键盘操作、可见焦点、字段标签和错误提示；新增/删除不能只依靠红绿色区分。

机会入口的具体流程待检索能力与需求范围验证后再设计；收件箱仅是候选呈现方式，
不代表已经确定招聘事件监测系统，不扩入当前档案/材料原型的首个交付目标。

## 4. 四条核心用户路径

### 建立背景

导入/粘贴资料 → 看原文与整理后的背景 → 核对新增事实和冲突 → 确认档案。

用户不需要重新抄一遍简历。已能识别的事实先展示，只针对关键歧义提问。
多个来源以用户指定的范围/优先级合并，不能简单用最新文件覆盖全部内容。
导入失败保留原件与可读错误，允许先手工整理；解析或模型生成完成不等于事实已确认。

### 手动修改

阅读正文 → 点击相应段落/字段 → 修改 → 保存草稿 → 确认相关事实或材料版本。

目标支持服务端草稿保存，明确显示“保存中 / 草稿已保存 / 保存失败”。保存失败保留输入，
离开时保护未保存修改。纯排版或材料措辞编辑不要求重新确认整份档案。
涉及职业事实变化时展示相应事实变更，不因保存材料而静默更新档案。

### Agent 修改与 Diff

选择内容 → 下达目标 → 生成持久化修改提议 → 就地审阅 → 接受/拒绝 → 形成新版本。

- 默认按段落/修改组展示增删；可展开前后对照、修改理由与来源。纯文本可显示行级 Diff，
  阅读模式不强制显示代码行号；富文本重点呈现内容与有意义的格式变化，不展示底层 JSON。
- 支持按修改组接受/拒绝或接受全部；有依赖的修改作为一组，不能拆到产生矛盾结果。
- 用户可要求调整提议；已接受内容不因重新生成被悄悄覆盖。拒绝不会修改当前正文。
- 首版 Agent 写入待审阅提议，不直接覆盖已确认版本。对无关段落不做顺手润色。
- 纯措辞提议的“接受修改”即确认该次材料变更，不再要求一次同义审批；含新事实的修改组
  在同一审阅过程中核对对应事实，未确认的部分不能成为正式填表依据。
- Agent 提出新的日期、数字、角色或成果时标出事实变化和来源；无依据时询问，不编造。
- 审阅通过后由服务端生成版本。重复点击不能重复应用；用户同时编辑过的内容必须重新
  对照，冲突时保留两边，不盲目覆盖或自动重放旧提议。
- 页面刷新、对话结束或流断开后仍能找回提议及实际状态；已接受变更不依赖聊天气泡存在。

### 更新与历史

继续编辑当前材料；查看版本时间、变更和来源；恢复旧内容时形成新版本，不抹除历史。
一旦某次申请选定并锁定材料，后续修改不改变当时的材料和证据。界面明确区分正在编辑的
内容与申请已使用版本；接受修改不等于授权投递。

## 5. 交互依赖的数据约束

- 职业事实的权威内容仍在领域后端。档案阅读页是这些事实的文档式呈现，不能另维护一份
  可独立漂移的 Markdown 事实库；自由编辑带来的事实变化先进入草稿与校验。
- 材料的可编辑正文与其版本由领域后端管理，编辑器文档是正文表示；导出的 Markdown、
  TXT、PDF 是派生结果，不分别维护三份权威正文。来源原件独立保留并建立引用。
- 精确修改绑定文档 ID、基准版本及稳定的段落/字段标识，并核对被替换内容。行号仅用于
  文本展示，不能作为富文本修改的唯一定位方式；过期提议不能直接写入最新版本。
- 提议、审阅结果、已确认版本与申请锁定关系需要持久化，并按当前用户校验归属。
  业务确认与外部执行授权分开，档案文字和来源中的指令不能自动授予工具权限。
- 草稿不会被默认作为正式填表依据；读取工具区分已确认事实、选定材料和参考来源。
  当前仅有并发控制 UUID 的档案表不等于已经实现这些版本能力。

这些是实现约束，不在本轮预建通用文档平台、多人实时协作或完整 Git 模型。
沿用现有编辑器与领域后端；Diff 展示、精确应用和持久审批需分别验证，不能把安装依赖
当成能力已完成。付费协作/版本服务不作为首版前提。

## 6. 交付顺序与验收

下一步先做可见交互原型：虚构但有真实复杂度的档案与一份材料，覆盖阅读、局部编辑、
Agent 修改入口、Diff 接受/拒绝及窄屏切换。可以用固定修改提议验证交互，但必须明确是
模拟数据；不把它记作真实 Agent、数据库版本或材料导入已经完成。

交互验证后，按一份材料贯穿导入、草稿、提议、确认与 Agent 读取的真实路径实施，具体
拆分与当前进度只维护在 STATUS。暂不同时展开所有格式、站点填表、自动投递和商业运营。
已有档案与用户隔离继续保留；数据模型演进需要迁移，不通过清空测试库掩盖兼容问题。

| 场景 | 完成标准 |
| --- | --- |
| 初次进入 | 能导入、粘贴或讲述背景；无需先填写整屏表单；无内容有清楚的开始入口 |
| 阅读与编辑 | 正文默认可读，字段按需编辑，能看原文与来源；长文和窄屏可用 |
| 精确修改 | “仅压缩这一段”只改变选定范围；用户能看到前后内容、理由并接受/拒绝 |
| 事实变化 | 纯措辞与新事实分开；不把无来源的数字或冲突信息自动确认为事实 |
| 持续更新 | 草稿、待审阅提议和已确认版本可区分；刷新后恢复；失败保留输入 |
| 并发与重复操作 | 旧版本提议不覆盖新编辑；重复接受不产生重复版本或重复修改 |
| 历史与申请 | 恢复产生新版本；后续修改不改变申请已使用材料 |
| 用户隔离 | 其他用户无法读取原件、正文、提议、历史或其下载地址 |

原型阶段验证前三项的交互并演示关键错误态；真实功能交付时验证对应服务端行为。
公开测试用虚构样本覆盖多来源覆盖范围、不同语言表达、论文状态和私人备注边界；
真实资料仅在另行明确的本地自用验收中使用，不进入 Git 或默认发送给模型服务。
