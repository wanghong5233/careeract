# CareerAct 工程协作

项目以单人维护、有限预算、自用和求职代表作为背景。先读 [STATUS](../../../docs/handbook/STATUS.md)，
再按问题定位材料；工作流程和文档归属以[开发手册](../../../docs/handbook/DEVELOPMENT.md#单人开发流程)
为准。Skill 辅助执行和判断，不建立平行 SOP，不要求每次修改都走完整流程。

## 从当前问题选择入口

| 请求或症状 | 判断与动作 |
| --- | --- |
| 下一步做什么，需求过多 | 对照 PRD、已实现能力、依赖、风险和可用时间，选择一个可验收目标；其他目标保留在 STATUS 的后续或暂缓项 |
| 不清楚要做成什么 | 先澄清用户问题与成功标准。产品形态用可见原型，技术不确定性用小实验，不以长计划掩盖未知 |
| 文档重复、过时或找不到 | 按作用域和读者用途核对权威位置；先看引用与独有依据，再合并或迁移，避免只改目录名 |
| 开始或恢复重要专题 | 核对工作区、专题当前状态、相关代码和证据；用最小任务继续，不重做已验证工作 |
| 收尾、交接或反复返工 | 检查实际结果与目标的差距，同步事实、剩余问题和下一步；改进缺失的验证或上下文，不累积通用规则 |

## 保持知识可用

- PRD 定义需求，ARCHITECTURE 定义系统边界；候选方案不得反向改写它们。
  面向全项目的规范/操作进入 handbook，具体工作台、Runtime 或选型研究进入对应 topic。
- 查到已有同一主题就更新或链接，避免为每轮任务创建新目录。小修不建文档；复杂专题从一份
  README 起步，需要时才补设计、原型或实验记录，不自动生成整套模板。
- 一次重要决定保留问题、选择、理由和影响；引用来源与验证日期，区分草案、已确认及已替代。
  设计确认、代码实现、验收通过分别表达，历史运行结果不冒充当前环境检查。
- 清理前区分重复内容、仍有效证据和真正失效内容。私人/未提交文件不能依赖 Git 恢复；
  迁移保留正文和忽略边界，修正全部引用，不把私人资料发布到公共文档或原型。
- 保留独立且有用的研究依据；当前结论只维护一处。STATUS 不复制细任务、参数或完整研究。
  新会话只读取当前工作所需内容，不全量加载专题历史或研究参考。

## 让推进方式匹配任务

- 对明确的小改动直接实施和检查。跨服务、行为不明或有重要副作用时，先明确范围与验收。
  已有授权不重复确认，范围扩大或重要产品取舍才交给用户判断。
- UI 形态变化用少量效果图或现有页面沟通，确认方向后直接迭代正式前端；复杂交互才按需
  做最小原型，不强制同时交付图片和独立实现。已有原型可继续利用，用户确认与技术检查分开记录。
- 业务功能按完整路径验证输入、结果及适用的隔离、并发和恢复；Runtime 调优先固定可比较的
  样本、环境、指标和成本边界。不把单次输出或模拟链路当成普遍成功。
- 用户、任务和执行证据优先于文档数量。先完成一个可验证增量，再按新发现调整下一步。
  auth/web/debug 等专业实现按需读已有技能，不把本技能扩成认证、前端或排障教程。
- 交付时更新受影响文档、实际检查和限制；提交与外部操作按授权处理。工程检查通过不等于
  产品已验收或已经部署。阻塞与暂停写明恢复条件，不能勾成完成。

评估或调整管理方式时才读[调研依据与取舍](references/research.md)。观察能否更快恢复上下文、
更早发现偏差、减少重复维护；文档负担增加时先裁剪，不默认引入流程工具、更多 Skill 或审批。
